Monorepo Architecture Approaches

How to organize packages, shared code, and deploy targets

A

Apps + Packages (Recommended)

Separate apps/ for deployable targets and packages/ for shared libraries. Standard Turborepo convention.

pebbledesk/
├── apps/
│ ├── web/ — React + Vite SPA (dashboard)
│ └── api/ — Hono on Cloudflare Workers
├── packages/
│ ├── db/ — Drizzle schema, migrations, Neon client
│ ├── auth/ — Better Auth config, shared auth utilities
│ ├── shared/ — types, validators (Zod), constants
│ └── ui/ — Shadcn components, Tailwind config
├── turbo.json
├── package.json
└── pnpm-workspace.yaml

Pros

  • Clear separation: deployables vs libraries
  • Standard Turborepo pattern — well-documented
  • Easy to add marketing site later as apps/marketing
  • DB package reusable if you ever add a cron worker

Cons

  • More packages to configure initially
  • Import paths need package.json exports setup
B

Flat Packages

Everything under packages/ — no apps/ distinction. Deployables and libraries are siblings.

pebbledesk/
├── packages/
│ ├── web/ — React + Vite SPA
│ ├── api/ — Hono on Workers
│ ├── db/ — Drizzle schema + migrations
│ ├── auth/ — Better Auth config
│ ├── shared/ — types, validators
│ └── ui/ — Shadcn + Tailwind
├── turbo.json
├── package.json
└── pnpm-workspace.yaml

Pros

  • Simpler — one directory, no apps/packages split
  • Fewer nesting levels

Cons

  • No visual distinction between deployables and libraries
  • Less conventional — new contributors need to figure out what deploys
C

Minimal (API Inside Web)

The API lives as a route handler inside the Vite app. One deployable, shared code is just src/ directories.

pebbledesk/
├── src/
│ ├── app/ — React SPA routes & components
│ ├── api/ — Hono routes (mounted via Vite plugin)
│ ├── db/ — Drizzle schema
│ ├── auth/ — Better Auth
│ └── shared/ — types, validators
├── package.json
└── vite.config.ts

Pros

  • Simplest possible setup — one package.json
  • No cross-package imports to configure
  • Fastest to scaffold

Cons

  • API and frontend are coupled — can't deploy independently
  • Can't share DB/auth with a future cron worker or marketing site
  • Doesn't match the graduation stack architecture
